# Этап 1 — дизайн-спецификация Sticker Workspace

Статус: **на согласовании**. Общий стиль №7 Specimen Catalogue и группировка по стадиям из №8 Production Ledger уже выбраны пользователем. Это спецификация экранов перед изменением React-клиента; приложение на этом этапе не редизайнилось. После согласования этот документ и [`tokens.json`](tokens.json) становятся источником истины для этапов 2–5.

## 1. Что именно утверждаем

Белый каталог без маркетингового hero, «стекла», свечения, градиентных карточек и повторяющихся статистических панелей. В первом экране — поиск и сами стикеры. Пастельные подложки относятся только к области превью, а не к интерфейсной рамке. Режим **Processing** использует три фактических статуса (`captured`, `failed`, `converted`) из идеи №8, но остаётся частью той же светлой системы. `converting` показывается отдельной строкой текущей работы, если такая запись есть; состояние файлового здоровья не подменяет статус конвертации.

Основной язык UI первого релиза — **английский**, как в нынешнем клиенте и одобренных концептах. Это сохраняет объём редизайна без отдельной локализации. Русский перевод можно добавить позже без изменения структуры. Все цифры, даты, имена, изображения и теги в PNG-макетах иллюстративные; приложение берёт их только из локального API. Изображения стикеров в макетах не являются пользовательскими файлами.

## 2. Каркас, навигация и URL

- Desktop ≥960 px: верхняя полоса 60 px, слева `Sticker Workspace`, по центру ссылки `Library`, `Processing`, `Import`, `Storage`, `Archives`, справа кнопка состояния локального сервиса. Основная область — белая, максимум 1480 px, поля 32 px (24 px на ноутбуке). Ни один статусный блок не отодвигает первый ряд каталога за первый экран.
- Mobile <640 px: верхняя полоса 56 px с брендом и кратким состоянием; фиксированная нижняя навигация 64 px + safe-area: `Library`, `Processing`, `Import`, `More`. `More` открывает меню со ссылками `Storage`, `Archives` и подробным статусом. На экранах деталей и редактора нижняя навигация скрыта, есть явная ссылка «назад». Переключение не сбрасывает поиск и позицию каталога.
- При ширине 640–959 px: компактная верхняя навигация без фиксированного нижнего бара. Ссылка `More` объединяет `Storage` и `Archives`, если все пять пунктов не помещаются без переноса. Нельзя скрывать критические пункты только за hover.
- `DevTools` не является основной вкладкой. Кнопка состояния раскрывает различимые состояния `Offline/manual`, `Awaiting opt-in DevTools`, `Last asset accepted`, `Local delivery failed`, `Budget exhausted`, `Disconnected`. Поле `listening: null` сейчас **не доказывает**, что DevTools открыт; UI не пишет «Listening» без нового достоверного сигнала. Успешный ручной импорт не меняет live-status.
- Ссылки навигации имеют адреса состояния в рамках SPA: `?view=library`, `?view=processing`, `?view=import`, `?view=storage`, `?view=archives`, `?view=detail&id=…`, `?view=editor&id=…`. Поиск, тип, сортировка и страница каталога отражаются в query (`q`, `type`, `sort`, `page`); Back/Forward восстанавливают их. Переходы реализуются настоящими ссылками, не кликабельными `div`.
- При открытии деталей с мобильной библиотеки Back возвращает к прежним фильтрам и позиции прокрутки. Невыполненные правки в редакторе требуют подтверждения перед выходом; закрытие просмотра без правок — нет.

## 3. Дизайн-система

Машинно-читаемые значения — в [`tokens.json`](tokens.json). Цветовой замок: фон и поверхности **#FFFFFF**, не кремовые; основной текст `#111820`, вторичный `#5D6B80`, граница `#D7DEE8`, функциональный фиолетовый `#5133D4`. Состояния — зелёный `#087A46`, янтарный `#9A5B00`, красный `#B42318`, всегда с текстом и/или пиктограммой. Контраст этих цветов к белому проверен как ≥5.4:1 для обычного текста. Шахматная прозрачность — только внутри media-превью или по явному переключателю.

Типографика — локальный системный sans-stack без сетевой загрузки: заголовок страницы 28 px desktop / 24 px mobile, секции 20 px, текст 16 px, controls и метаданные 14 px. Никаких браузерных размеров по умолчанию для кнопок. Числа и длительности — `tabular-nums`. Подписи не обрезаются без доступного полного имени: карточка делает 1–2 строки с ellipsis, инспектор показывает имя целиком с переносом.

Базовые интервалы 4/8/12/16/24/32/48 px; радиусы 6 px для плитки, 8 px для управления, 12 px для диалога. Контролы и touch targets минимум 44 px по высоте. Focus-visible — непрерывный 3 px контур `#B8A7F5` с 2 px отступом, не заменяемый одной сменой цвета. Наведение/нажатие усиливает контраст границы и/или фона; `disabled` сохраняет читаемость и объяснение причины. Анимация — только opacity/transform по 120–180 ms, без `transition: all`; `prefers-reduced-motion` отключает несущественное движение и автопроигрывание превью.

Пастельные поверхности превью: peach `#FBE6E2`, blue `#E0F0FF`, lilac `#F0E9FF`, lemon `#FFF5C7`, mint `#E7F8EB`, dark `#31353A`. Назначение устойчиво по ID, не меняется при сортировке. Пользователь может включить шахматную подложку для всех превью; выбранное значение локально сохраняется с версией настроек. Не рисуем «новый стикер» поверх реального изображения: `object-fit: contain`, его края не обрезаются.

Семейства компонентов: `AppHeader`, `PrimaryNav`, `StatusPopover`, `PageHeading`, `SearchField`, `FilterTabs`, `SortSelect`, `ViewToggle`, `StickerTile`, `StageRow`, `StickerInspector`, `MediaPreview`, `TagEditor`, `ImportDropzone`, `ImportResultRow`, `IssueRow`, `ArchiveRow`, `InlineAlert`, `ConfirmLeaveDialog`, `Toast`. Один и тот же action/button style используется во всех режимах, различия оформлены вариантами. Иконки — один outline-набор с толщиной 1.75–2 px; семантика: grid/list, search, upload, queue, archive, warning, download, edit, retry, close, back. Декоративные иконки скрыты от screen reader, иконки без текста имеют `aria-label`.

## 4. Точные компоновки и сценарии

### Library

- Desktop 1440×900: шапка 60 px; заголовок + счётчик, справа `Import files`; ниже единая строка поиска/типа/сортировки/вида/прозрачности. Первый ряд миниатюр начинается не ниже **280 px** от верха viewport. При 390×844 мобильная шапка, заголовок, поле поиска и одна строка фильтров занимают ≤320 px до первого превью. Никакой отдельной полосы с тремя огромными счётчиками и длинного предупреждения над сеткой.
- Сетка: ≥1280 — 5 колонок, 960–1279 — 4, 640–959 — 3, 360–639 — 2, <360 — 1. Gap 14/12 px, карточка состоит из media-поля 4:3, названия, типа + размеров, до двух тегов; дополнительная информация раскрывается в деталях. Размер в байтах — только при реальном поле API. `Animated` обозначается словом и кнопкой паузы/воспроизведения в preview, а не цветом.
- `All`, `Static`, `Animated` показывают реальные динамические количества. Search ищет ID, `originalFilename`, ручные теги. Сортировки первого релиза: `Newest first` (по `capturedAt` со стабильным tie-break ID), `Oldest first`, `Name A–Z`. Нет результата — текст `No stickers match your search`, действие `Clear filters`; пустая библиотека — `No stickers yet` и `Import files`. Смена фильтра сбрасывает `page=1`.
- За один запрос/страницу показывается **24 записи**, далее `Next`/`Previous` и номер страницы (не бесконечная полоса в десятки тысяч px). Все 1000 синтетических записей не должны попадать в DOM одновременно. Изображения ниже первого экрана — lazy, размеры заданы заранее. Выбор одной плитки открывает инспектор; это **не** обещает массовые операции. На desktop ≥1100 px инспектор 380 px справа, контактный лист остаётся видимым; на mobile это отдельный полноэкранный view.

### Sticker details

- Превью исходника/результата, имя и копирование ID, тип, пиксели, длительность/кадры для анимации, `status`, `health`, теги; ключевые действия `Edit sticker`, `Convert`/`Re-convert`/`Retry`, `Download WebP/WebM` по состоянию. Таб `Telegram` доступен только при существующем `convertedPath` **и** отсутствии `missing_converted`; иначе `Output missing` с объяснением. `Download` блокируется при отсутствии результата. Если `missing_original`, повторная конвертация блокируется; имеющийся результат, если он существует, можно скачать отдельно.
- На desktop инспектор — не модальный: focus переходит на его заголовок, Tab может идти дальше по странице; Escape закрывает, focus возвращается к выбранной плитке. На mobile экран деталей имеет back-link, а действия располагаются в нижней фиксированной области с безопасным отступом; контент не закрывается этой областью.
- Теги редактируются одной строкой с удалением chip-кнопкой, Enter добавляет тег, Save применяет через существующий `POST /api/stickers/:id/tags`; на ошибке старые теги остаются, поле показывает исправимое сообщение. Автосохранение не предполагается.

### Processing

- Порядок: `Captured` (очередь ещё не конвертированных), `Failed` (ошибка и явный Retry), `Converting` если есть, `Converted` (контактный лист результатов). Статусы берутся из API, а не вычисляются по наличию файла. Секция `Converted` не называется `Ready`: health `missing_converted` остаётся видимым, скачивание отключено. `Failed` с `missing_original` показывает почему Retry недоступен.
- На desktop первые две секции — компактные строки с миниатюрой, именем, причиной/подсказкой и действием; converted — плотный grid. На mobile строки идут вертикально без горизонтального overflow, главное действие остаётся крупным. Секция с нулём записей может быть свернута до одной спокойной строки, но не исчезает из логики навигации.
- Сообщения ошибок берутся из `sticker.error`, переводятся в безопасную понятную формулировку; нельзя придумывать причину вроде «WebP unsupported». Не выводить raw stack/путь к приватным данным. Ссылка `Storage health` показывает реальный счёт проблем отдельно от числа failed.

### Editor

- Desktop: отдельная рабочая поверхность с preview/кадрами слева и настройками справа; mobile: preview → `Animation slice` → `Transform` → `Outline` → `Text`, две последние группы сворачиваются. Имеющиеся функции сохраняются: scale 0.5–2.0, rotation −180…180°, outline on/off + width 1–20 px + color, top/bottom text до 100 символов; UI-валидация использует диапазоны не шире backend. У каждого поля настоящая label и единица измерения.
- Для анимированного источника выбирается **начало**; итоговый фрагмент не более 3 s, конец вычисляется. Один thumb, клавиатурные стрелки/Home/End; подсказка `Selected: 0.4–3.4 s (3.0 s)` и `Source: 4.8 s`. Для короткого источника окно укорачивается автоматически. Для статического стикера filmstrip/timeline не показывается.
- `Original` — неизменённый исходник, `Telegram` — preview текущих настроек; переключение не теряет форму. `Save & convert` блокируется только во время запроса, показывает `Saving…`, затем успех или исправимую ошибку. Пока есть несохранённые изменения, Cancel/Back/Escape открывает `Discard changes?` с `Keep editing` и `Discard`; `beforeunload` предупреждает об уходе из вкладки.

### Import

- Остаётся строго локальным: drag/drop и `Choose files` имеют одинаковый результат и клавиатурную альтернативу. Поддерживаемые UI-расширения сверяются с сервером: PNG/JPG/WebP/GIF/TIFF/AVIF/MP4/WebM/MOV/MKV/M4V. Необязательно перечислять все в первом экране, но доступен полный список и лимиты; до точного ответа сервера не обещаем успешную конвертацию. Флажок `Convert to Telegram format after import` по умолчанию сохраняет нынешнее поведение.
- Desktop 60/40: слева dropzone, справа результат текущего batch. Mobile: dropzone над списком, первая строка результата должна появляться в первом viewport после отправки. По каждому файлу: `Accepted`, `Duplicate`, `Failed` и действие/исправление из ответа `/api/import/files`; общий `413` отображается над списком, не как выдуманный per-file result. Счётчики `imported`, `duplicates`, `failed` берутся из API. Результат живёт в памяти текущего экрана; persistent history не обещан.
- Успешный manual import не меняет `DevTools` на ready/listening. HAR UI не включён до отдельного локального capability-теста. Нет облачной загрузки и автоматической публикации в Telegram.

### Storage Health

- Верх экрана показывает актуальную сводку из `GET /api/status`: число проблем и счётчики `missing original`, `missing output`, `orphan files`, `temporary entries`, `interrupted conversions`. Категории не складываются в число повреждённых стикеров: orphan/temp могут не соответствовать записи, а у одной записи может быть несколько флагов. Различаем `No issues found` и `Could not check storage`.
- Таблица/список конкретных проблем на макетах — **планируемая** возможность, которой текущий API не предоставляет. Фильтры по категории, ID записи и `Open sticker` допустимы только после read-only контракта из §6. Для orphan/temp — только тип, относительное безопасное имя и контекст; не выводить произвольный абсолютный путь и не предлагать `Delete`.
- Пока подробного endpoint нет, экран содержит сводку и честную строку `Item-level details are not available yet`. Кнопка `Run check` не должна имитировать полную проверку: либо повторно запрашивает существующий статус и явно называется `Refresh summary`, либо появляется с новой проверяемой операцией. Нет автоматического исправления и удаления.

### Archives

- Текущий контракт позволяет **создать** snapshot. Форма показывает назначение, предупреждение о локальном размере и диалог подтверждения; прогресс без серверных событий не выражается вымышленным процентом. После успеха выводятся имя/путь и число записей ровно из ответа сервера, если поля есть; иначе только подтверждённый факт создания.
- Список архивов, размер, manifest и действие `Verify` на макете — **планируемые** read-only возможности. До появления API экран честно показывает `Archive history is not available yet` и `Create archive`, без выдуманного списка. Verify сообщает `Verified`, `Mismatch` или `Could not verify` только после реальной проверки hash manifest и файлов сервером. Никакого `Restore` в первом релизе.
- На mobile будущий список — одна колонка с датой, именем, проверенным состоянием и действиями во второй строке. Никакой таблицы с горизонтальной прокруткой или кнопок размером меньше 44 px.

## 5. Состояния, тексты и переходы

| Ситуация | Что видно | Действие |
| --- | --- | --- |
| Первый запрос выполняется | Шапка и стабилизированный skeleton площади первых карточек, без ложных счётчиков | Дождаться; focus не прыгает |
| Пустая библиотека | `No stickers yet` и короткое пояснение локального импорта | `Import files` |
| Поиск/фильтр без совпадений | `No stickers match your search` с активными условиями | `Clear filters` |
| Сервер недоступен при старте | `Cannot connect to local service`; старые данные не выдаются за текущие | `Retry connection`; инструкция запустить локальный сервер |
| WebSocket оборван после загрузки | Существующие записи остаются видимыми с пометкой `Updates paused` | `Reconnect`; операции проверяются отдельными HTTP-ошибками |
| Истёкшая/недействительная session | `Session expired` без технических токенов | `Reconnect` / перезагрузить локальную страницу |
| Импорт: частичный успех | Раздельные счётчики и строка на каждый файл из ответа | `View imported`; исправить причины failed |
| Импорт: запрос целиком отклонён | Общая ошибка, например `Files exceed the upload limit`; нет фиктивных строк | Повторить меньшей партией |
| Сконвертирован, но output отсутствует | `Output missing`; статус `converted` не переписывается | Download выключен; `Re-convert` только при наличии оригинала |
| Original отсутствует | `Original missing` и флаг health | Edit/retry выключены; существующий output остаётся доступен, если здоров |
| Ошибка сохранения тегов/редактора | Исходные данные и введённые параметры сохранены в форме | Исправить и повторить |
| Создание архива не удалось | `Archive could not be created`; не утверждать, что файл существует | Повторить после выяснения причины |
| Storage summary недоступна | `Storage check unavailable`, а не `0 issues` | `Refresh summary` |
| DevTools не включён | `Manual mode` / `Awaiting opt-in DevTools` по достоверному API | Краткая подсказка, без ложного `Listening` |

Все сообщения об ошибках рядом с соответствующей формой/действием; transient success сообщается через `role=status`, error — через `role=alert` без повторного озвучивания каждого WebSocket-события. Toast не является единственным местом, где сохраняется важная причина сбоя. Условные действия не просто скрываются: при отсутствии исходника или результата объяснение остаётся текстом у соответствующей операции.

## 6. Контракт данных и граница реализации

| UI | Действующий источник | Что добавлять только с серверным контрактом |
| --- | --- | --- |
| Каталог, статусы, теги, media | `GET /api/stickers`, WebSocket `init/new_sticker/sticker_update`, `POST /api/stickers/:id/tags` | Размер файла в байтах, если нужен; нельзя вычислять его из вымышленного PNG |
| Статус сервиса и Storage summary | `GET /api/status`, `GET /api/session` | Достоверный сигнал DevTools listening; детальная проверка файлов |
| Импорт | `POST /api/import/files` с `imported`, `duplicates`, `failed`, `results` | Постоянная история batch/job; не предполагается текущим ответом |
| Редактор и output | Существующие `/api/stickers/:id/frame/:frameIndex`, `/api/convert` и edit routes | Undo/history или отдельный live preview, если текущий edit API их не обеспечивает |
| Архив | `POST /api/library/archive` | `GET /api/library/archives` и read-only verify-операция |

Предлагаемые API дополнения для этапа 5, после просмотра модели данных и тестов: `GET /api/storage/issues` возвращает категории, безопасный ID/относительное имя и признак связи с записью; `GET /api/library/archives` возвращает только созданные приложением архивы из разрешённой директории; `POST /api/library/archives/:id/verify` запускает **read-only** проверку manifest/hash без восстановления или удаления. Точные формы JSON и лимиты устанавливаются при backend-дизайне, не выводятся из картинок. Все новые маршруты наследуют локальную session/origin защиту и не принимают произвольный путь из UI.

Режим `Processing` строится из серверного `status`, а `health` накладывается независимой предупреждающей меткой. Пока новые endpoints не готовы, можно выпускать библиотеку, импорт, редактор и сводку Storage с честно ограниченным функционалом. Макеты не разрешают подменять отсутствующие данные статическими примерами.

## 7. Правила реализации и проверки

- Семантические `a` для переходов, `button` для действий, `label` для всех полей; начальный `Skip to content`. Focus-visible, разумный DOM order, закрытие popover по Escape и клику вне, возврат фокуса при закрытии инспектора/диалога. Настоящий `<dialog>` либо эквивалент с trap focus и восстановлением focus для подтверждения потери правок.
- Поддержать 320, 360, 390, 640, 768, 960, 1280, 1440 px. Проверить клавиатуру, 200% zoom, длинные имена, пустые теги, разные media aspect ratio, системный reduced motion. Нет горизонтального overflow ни у страницы, ни у карточек; sticky/mobile действия не закрывают последний элемент.
- `App.jsx` делится по экрану/домену состояния, общие UI-компоненты не знают о способе получения данных. Query и WebSocket обновления не сбрасывают фокус/фильтр. Селекторы групп/счётчиков выводятся из одного snapshot; обновление записи не меняет самовольно текущую страницу.
- Каталог использует 24 записи на странице и заданные размеры media; `loading=lazy` ниже первого экрана. Editor и тяжёлые preview-модули загружаются по маршруту. Поиск может использовать `useDeferredValue` при замерах задержки ввода; мемоизация и виртуализация — по профилю, не по привычке. Существующие 102 записи не оправдывают постоянный DOM из 102 длинных mobile-карточек.
- Сравнивать Browser-рендер с desktop/mobile PNG по иерархии, плотности, геометрии и цвету, а не по сгенерированным персонажам и тексту. `npm run check`, URL navigation, keyboard-only, import/duplicate/partial failure, static/animated edit и 1000-record fixture — обязательные проверки этапов 2–6.

Правила доступности и интерфейса основаны на [Web Interface Guidelines](https://github.com/vercel-labs/web-interface-guidelines); конкретные решения о responsive layout и текстах — проектные решения для этого приложения, а не цитаты из руководства.

## 8. Приёмка этапа 1 и граница следующего этапа

На согласование выносится **один** светлый дизайн-язык, включая Processing, без тёмной параллельной темы. Отдельно важно подтвердить: (1) English-first подписи, (2) навигацию с пятью разделами и mobile `More`, (3) 24 записи на страницу вместо бесконечной сетки, (4) право показать Storage/Archives сперва в ограниченной версии, пока не добавлены read-only API. Контент, имена и мелкие метки на сгенерированных изображениях могут противоречить точным правилам выше; при реализации побеждают §4–6 и реальное поведение сервера.

До согласования этапа 1 не меняем React, CSS и API. После него этап 2 начинает структурное разделение клиента с сохранением поведения; новую визуальную систему и функциональные расширения вводим по этапам с Browser-проверкой против этих макетов.
