# План доработки расширения Sticker Capture (v3)

Состояние: 26 сентября 2026 года, согласован пользователем (решения — §5). Ветка `extension/capture-v3` от `master` (`530befa`, редизайн этапов 0–7 влит).

## 1. Что есть сейчас

MV3-расширение `extension/` (≈1 900 строк) без content script: `devtools.js` слушает `chrome.devtools.network.onRequestFinished`, фильтрует ответы по `shared/sticker-policy.json` (хосты CDN, маркеры пути, MIME), читает уже загруженное тело через `getContent()` и отдаёт его `background.js`. Тот складывает payload в IndexedDB-очередь (дедуп по SHA-256) и доставляет на `http://127.0.0.1:3001/api/ingest` с Bearer-токеном, с backoff и блокировкой при 4xx. Popup — настройки (URL, токен, включение) и статус; DevTools-панель — четыре счётчика и последнее событие.

Сервер (`server.js:650`) валидирует payload той же политикой, перекодирует в WebP, дедуплицирует, считает **session budget** (25 уникальных захватов / 20 минут, `lib/sessionBudget.js`) и rate limit 40/мин.

Сильные стороны, которые сохраняем: никаких запросов к TikTok/CDN, никакого DOM, минимальные permissions (`storage`, `alarms`, host только loopback), durable очередь, общая политика URL у сервера и расширения, 12 unit-тестов shared-модулей.

Наблюдение по данным: в библиотеке 114 записей, из них 90 — ручной импорт, но большинство «ручных» файлов называются как ответы CDN TikTok (`…~tplv-dhq7zx4c1p-video2sticker-mid.webp`, `…-photo-comment-full.webp`). То есть основной реальный путь — сохранять файлы из TikTok вручную и импортировать; расширение должно сделать этот путь короче, не увеличивая риск.

### Удобство и полезность

- **Настройка токена**: сгенерировать в popup → вставить в `.env` → перезапустить сервер. Самый частый источник `Token rejected`.
- **Панель ничего не показывает о самих стикерах**: только счётчики. Не видно, что поймано, что уже есть в библиотеке, что отклонено и почему.
- **Потеря уже загруженного**: если захват был выключен, стикеры, загруженные при открытом DevTools, теряются. Единственный способ «повторить» — перезагрузить чат, то есть **создать лишний трафик**.
- **Dashboard не знает, работает ли слушатель** (`listening: null`); SPEC §6 прямо называет «достоверный сигнал DevTools listening» недостающим контрактом.
- **Качество**: TikTok отдаёт в чате вариант `-mid` (в основном 240×240); при открытии стикера крупно может прийти `-full`. Сейчас это две независимые записи-дубликата, а лучший вариант не выбирается.
- **Устаревание политики**: если TikTok сменит хост или шаблон пути, захват молча перестанет работать — нет даже счётчика «похоже на стикер, но отклонено».
- Новые захваты не конвертируются автоматически, в отличие от ручного импорта.

### Риск блокировки — что реально влияет

Расширение **не создаёт трафика к TikTok** и не трогает страницу, поэтому основные факторы риска лежат вне его кода:

1. **Открытый DevTools** — сам по себе сигнал, который страница может заметить (размер окна при пристыкованной панели, anti-debug приёмы). Расширение это скрыть не может и не должно пытаться.
2. **Поведение аккаунта** — быстрая прокрутка длинной истории, частые перезагрузки чата ради повторного захвата.
3. **Кэш** — включённый в DevTools `Disable cache` меняет профиль запросов (все стикеры перекачиваются заново).

Текущие «защитные» меры частично промахиваются: session budget и пауза с jitter (`CAPTURE_MIN_INTERVAL_MS`, `CAPTURE_JITTER_MS`) ограничивают только запись на localhost, на трафик к TikTok они не влияют. Жёсткий отказ по бюджету даже вредит: он подталкивает перезагрузить чат после сброса. Полезная часть бюджета — напоминание о длине сессии — сохраняется, но как мягкий сигнал.

Проверено, что поверхность обнаружения расширения минимальна: нет `content_scripts`, `web_accessible_resources`, `externally_connectable`, поэтому страница не может его пробировать. Это нужно зафиксировать тестами, чтобы не потерять при доработке.

### Дизайн

Popup и панель — тёмная тема со свечением (`#090d1a`, `#8b5cf6`), своя типографика, нет иконки расширения (серый пазл), название `TikTok DM Sticker Capture` не совпадает с `Sticker Workspace`, словарь статусов расходится с popover dashboard (`Listening` против сознательно честного `Awaiting DevTools`).

## 3. Порядок работ

### Этап E0. Страховочные тесты (0.5–1 день) — выполнен, [E0.md](E0.md)

1. Тест-инварианты manifest: permissions ⊆ {`storage`, `alarms`}, host permissions только loopback, нет `content_scripts`, `web_accessible_resources`, `externally_connectable`, `debugger`, `tabs`, `webRequest`, `scripting`.
2. Статический тест кода расширения: `fetch` только к нормализованному loopback URL и к собственным `chrome.runtime.getURL` ресурсам; нет `chrome.devtools.inspectedWindow.eval`, `reload`, `chrome.scripting`.
3. Тест `background.js` в `vm` с mock `chrome.*` и fake IndexedDB: ack, duplicate, block, retry, wait. Покрыть B1/B2 падающими тестами до исправления.

**Готово, когда:** инварианты безопасности проверяются в `npm test`, а поведение очереди воспроизводимо без браузера.

### Этап E1. Исправление ошибок (1–2 дня) — выполнен, [E1.md](E1.md)

1. B1: heartbeat обновляет только `lastHeartbeatAt`; журнал событий — отдельный кольцевой буфер последних 20 событий.
2. B2: отдельное действие `pause` для 429 с `budgetExhausted` → состояние `Paused: capture budget`; элементы держатся в очереди без повторов до сброса бюджета; `Retry-After` учитывается для обычного 429.
3. B3: классификация по URL (хост + путь), тип — по magic bytes; заголовок только как подсказка. Добавить `image/awebp`, `application/octet-stream` в допустимые заголовки; AVIF — только после подтверждения на реальном ответе.
4. B4: слушатель активен только при `captureEnabled` и если `inspectedWindow` открыт на `https://www.tiktok.com/*` (URL определяется по `network.onNavigated` и документу страницы из `getHAR()`; без `inspectedWindow.eval` и без новых permissions). Статусы: `Off`, `DevTools not open`, `DevTools open on another site`, `Watching TikTok tab`.
5. B5: сервер разделяет `lastRejectedReason` (содержимое не прошло политику) и `lastDeliveryError`; dashboard показывает `Delivery failed` только для второго.
6. B6: исправить тексты README, popup, panel, ACCOUNT_SAFETY.
7. B7: порт настраивается в popup (optional host permission для `127.0.0.1:*` запрашивается по требованию) либо сервер печатает понятную подсказку при `PORT≠3001` — выбрать при реализации, по умолчанию 3001.
8. B8: для заблокированных элементов — `Discard` и `Save file` (Blob-ссылка из страницы расширения, без permission `downloads`), чтобы файл можно было импортировать вручную.
9. Снизить `maxBodyBytes` с 12 MB до значения по реальным ответам (+запас), чтобы очередь 500 элементов не занимала гигабайты.

### Этап E2. Подключение и честный статус (1–2 дня) — выполнен, [E2.md](E2.md)

1. **Pairing без `.env`**: в popover/Health dashboard кнопка `Connect extension` — сервер генерирует токен, хранит его в `output/.ingest-token` (0600, вне Git), показывает один раз для копирования; popup принимает вставку. `INGEST_TOKEN` из `.env` продолжает работать и имеет приоритет. `Disconnect` отзывает токен. Live-capture на сервере включается только этим явным действием.
2. **Heartbeat в сервер**: пока слушатель активен, background раз в 20 с отправляет `POST /api/extension/heartbeat` (Bearer, только loopback) с состоянием `watching|off|other_site` и размером очереди. Dashboard показывает `Extension · Watching TikTok · 5 s ago`; без свежего heartbeat — прежнее честное `Awaiting DevTools`.
3. **Единый словарь статусов** для popup, панели и popover dashboard, описанный в SPEC расширения.

### Этап E3. Полезные функции (3–4 дня) — выполнен, [E3.md](E3.md)

1. **Лента сессии в DevTools-панели**: миниатюры пойманных стикеров (из тех же байтов, `blob:` URL), состояние каждого — `New`, `Already in library`, `Queued`, `Rejected: <причина>`; ссылка `Open in library` (`http://127.0.0.1:3001/?id=…`). Сервер уже возвращает `duplicate` и `sticker`.
2. **«Забрать из журнала Network»**: кнопка в панели вызывает `chrome.devtools.network.getHAR()` и прогоняет уже записанные с момента открытия DevTools ответы через ту же политику. Ноль сетевых запросов, спасает случай «забыл включить захват» без перезагрузки чата.
3. **Кэш известных хэшей** (LRU ~2 000) — повторно встреченный стикер не отправляется на сервер и сразу помечается `Already in library`.
4. **Auto-convert для захватов** — настройка сервера (по умолчанию как у ручного импорта), новые захваты попадают в одну задачу Jobs на сессию.
5. **Диагностика политики**: счётчик «похоже на стикер TikTok, но отклонено» с причинами и обезличенным шаблоном пути (без query), видимый только в панели — ранний сигнал, что TikTok сменил формат URL.
6. **Лучший вариант**: сервер сохраняет ключ ассета TikTok (хэш перед `~tplv`) из очищенного URL; при захвате варианта с большим разрешением у записи с тем же ключом UI предлагает оставить лучший. Без удаления файлов, по правилам проекта.

### Этап E4. Снижение риска блокировки (0.5–1 день, параллельно с E1–E3) — выполнен, [E4.md](E4.md)

1. Session budget → **мягкая пейсинг-подсказка**: счётчик и таймер сессии в панели и popup, предупреждение после N захватов / M минут; жёсткий лимит остаётся настраиваемым, но по умолчанию только ставит очередь на паузу (E1.2), не теряя данных. *(Требует решения, см. §5.)*
2. Панель при старте проверяет и напоминает: DevTools лучше открыть отдельным окном, не включать `Disable cache`, не перезагружать чат ради повторного захвата, прокручивать в обычном темпе, остановиться при CAPTCHA/предупреждении.
3. Обновить `docs/ACCOUNT_SAFETY.md`: реальные факторы риска (§2), что делает и чего не может расширение, честная формулировка остаточного риска.
4. Не добавлять ничего, что создаёт запросы к TikTok, читает DOM или маскирует DevTools; E0-тесты это охраняют.

### Этап E5. Единый дизайн (2–3 дня) — выполнен, [E5.md](E5.md)

1. Токены из `docs/redesign/stage1/tokens.json` → `extension/shared/tokens.css`; тест сверяет значения, чтобы они не разъехались.
2. **Popup** (360 px): светлая система Specimen Catalogue — шапка со значком и `Sticker Workspace · Capture`, строка статуса (точка + текст, как `status-pill`), тумблер захвата, счётчики сессии, блок `Connect` / настройки, свёрнутые под `Settings`; кнопки одного стиля с dashboard, focus-ring `#B8A7F5`.
3. **DevTools-панель**: те же компоненты, но следует теме DevTools (`chrome.devtools.panels.themeName`): светлый вариант — токены как есть, тёмный — производная палитра с сохранением контраста ≥ 4.5:1. *(Требует решения, см. §5.)*
4. Иконка расширения 16/32/48/128 и иконка панели; outline-иконки lucide (ISC) инлайном; badge-цвета из токенов (`accent`, `danger`, `textSecondary`).
5. Переименование: `Sticker Workspace Capture`; версия manifest `3.0.0`.
6. Доступность: `label` у полей, `aria-live` только для итогов, клавиатура, `prefers-reduced-motion`.

### Этап E6. Проверка и выпуск (1–2 дня)

1. `npm run check` + новые тесты E0–E3.
2. UI smoke popup и панели в headless Chrome по `file://` с shim `chrome.*` (установленный Chrome не загружает unpacked-расширения из командной строки): состояния Off / Watching / Paused / Delivery failed / blocked item, светлая и тёмная тема панели, отсутствие overflow.
3. Интеграционные тесты сервера: pairing, heartbeat, разделение reject/delivery error, 429 budget.
4. Ручная приёмка на тестовом аккаунте: один статический и один анимированный стикер, `Capture from Network log`, проверка в Chrome Network, что расширение не создало запросов к TikTok/CDN.
5. Отчёт `docs/extension/E<n>.md` по каждому этапу, как в редизайне.

Оценка: **9–15 рабочих дней** на E0–E6, из них 1–2 дня — выбор лучшего варианта (E3.6).

## 4. Границы

- Никаких content script, DOM, кликов, скролла, `debugger`/CDP, `webRequest`, повторных запросов к TikTok/CDN и маскировки DevTools.
- Данные уходят только на loopback. Токен не попадает в Git, логи, URL.
- Ручной импорт остаётся режимом по умолчанию; live-capture включается явным действием.
- Существующие записи, файлы и паки не меняются; миграций базы нет, кроме добавления необязательных полей (ключ ассета).

## 5. Решения пользователя (26.09.2026)

1. **Бюджет сессии** — мягкая подсказка: счётчик и таймер сессии с предупреждением; при превышении очередь ставится на паузу без потери данных (E1.2, E4.1).
2. **Тема DevTools-панели** — следует теме DevTools; popup всегда светлый (E5.3).
3. **Pairing через dashboard** — да, кнопка `Connect extension`; `INGEST_TOKEN` из `.env` сохраняет приоритет (E2.1).
4. **Объём цикла** — включены автоконвертация захватов (E3.4, по умолчанию включена, как у ручного импорта, с переключателем), «Забрать из журнала Network» (E3.2) и выбор лучшего качества `-mid`/`-full` (E3.6).
