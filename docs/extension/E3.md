# Этап E3 — полезные функции

Состояние: 27 сентября 2026 года, выполнен.

## Что сделано

1. **Общий конвейер захвата** (`extension/shared/capturePipeline.js`) для живого слушателя и для журнала Network: классификация URL, чтение тела только через `getContent()`, тип по байтам, миниатюра, отправка в background. Определение сайта вкладки и классификация перенесены туда же.
2. **Лента сессии в панели DevTools.** Миниатюра 96 px (WebP ≤ 40 КБ, создаётся из уже полученных байтов), состояние, время, источник (`from Network log`) и **Open in library** (`http://127.0.0.1:3001/?id=…`). Лента (до 60 записей) и счётчики живут в `chrome.storage.session`: только в памяти, до закрытия Chrome. Байты стикера в ленте не хранятся, миниатюра на сервер не уходит, небезопасные миниатюры (не `data:image/…`) отбрасываются. Записи, стоящие в очереди, показывают её текущее состояние (`Held`, пауза бюджета).
3. **Capture from Network log.** Кнопка в панели вызывает `chrome.devtools.network.getHAR()` и прогоняет записи через тот же конвейер: ни одного нового запроса. На чужом сайте отказывается. Итог — «Found N sticker responses: X sent to the library, Y already in library…»; без стикеров панель объясняет, что журнал содержит только запросы с момента открытия DevTools и что перезагружать чат не нужно. Записи HAR без `getContent` пропускаются.
4. **Кэш известных стикеров.** После подтверждения сервером расширение запоминает «хэш байтов → ID в библиотеке» (до 2000, `chrome.storage.local`, привязка к адресу сервера и хэшу токена; сброс при их смене). Повторно встреченный стикер не отправляется и сразу показывается как `Already in library`.
5. **Автоконвертация захватов.** Новые (не дубликаты) захваты через `/api/ingest` собираются в окно 4 с (не дольше 15 с) и конвертируются одной задачей Jobs «Convert N captured stickers». Создание задачи вынесено в общую `startConvertJob` — та же логика, что у `/api/jobs/convert`. Настройка по умолчанию включена, как в панели импорта; флажок в **Health → Capture extension**; хранится в `output/capture-settings.json` (`POST /api/extension/settings`).
6. **Диагностика политики.** Изображения с CDN TikTok (`diagnosticHostSuffixes` в `sticker-policy.json`), которые политика отклонила, считаются по причинам; хранятся до трёх примеров-шаблонов с замаскированными ID (`<id>`, `<n>`) и без query. Тела таких ответов не читаются. Панель показывает раскрывающийся счётчик с пояснением, какие записи ожидаемы (аватары), а какие означают смену формата ссылок TikTok.
7. **Лучший вариант.** `frontend/src/lib/variantModel.js` вычисляет ключ ассета TikTok (32 hex перед `~tplv`) и вариант (`video2sticker-mid`, `photo-comment-full`…) из URL захвата или имени импортированного файла — без изменения базы. В инспекторе — строка `TikTok variant` и подсказка «A larger capture of this TikTok sticker is in the library: 512×512 px instead of 240×240 px · Open it». На экране пака — **Use larger capture (512×512)**: замена сохраняет позицию и эмодзи, предлагается только для того же формата и если крупного варианта ещё нет в паке. Файлы не удаляются.

Проверка реальной библиотеки: у 108 из 114 записей есть ключ ассета (71 `video2sticker-mid`, 32 `photo-comment-full`, 5 `full`), пар вариантов пока нет — функция сработает на новых захватах.

## Ограничения

- Работу `getHAR()` и `getContent()` у записей журнала на реальной вкладке TikTok нужно подтвердить в E6: API документирован, но проверен только на подставных данных.
- Миниатюры создаются только в окне DevTools; в тестах vm их нет, и лента показывает заглушку с форматом файла.
- Список доменов для диагностики — предположение по известным CDN TikTok; он влияет только на счётчик, не на захват.
